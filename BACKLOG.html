The rollover switched off 378 people and told nobody

New, 25 Aug. Repaired by hand; the cause of one group is still unexplained. Recurs next August.

Activating 2026‑2027 on 21 Aug left 46 staff and 313 teachers switched off while still on the current roster, and a further 19 switched on but absent from it. All were repaired by hand between 24 and 25 Aug. Two of the three causes are now fixed in code. The third is not understood.

The whole investigation, so none of it has to be redone

How the flip works. Activating a year deactivates anyone holding an open assignment in the outgoing year with none in the incoming one — absence from the roster is read as departure. Only NETWORK_ADMIN is exempt, so teachers go the same way as everyone else.

Cause 1 — a later upload could not switch anyone on. The flip switched people off; a roster uploaded afterwards wrote their assignment and never touched is_active, because syncDenormalised only ever wrote role and school. 46 staff, mostly Home Office network leaders, and 250 teachers. Fixed: a live upload now switches on anyone it names and says so per row.

Cause 2 — reactivating wrote the flag and not the roster row. toggle-active flipped is_active only, so the account looked active and 403’d on every request — a dashboard for a few seconds, then a white screen. 19 people, found because one of them reported it. Fixed: reactivation writes the assignment, and that 403 now lands on a page that explains itself instead of dying.

Cause 3 — still unexplained. 63 teachers were new hires: no 2025‑2026 assignment at all, so the flip never considered them. A staged upload creates a new hire inert on purpose, so nothing takes effect before activation, and step 4b of activateSchoolYear is meant to switch them on — its condition covers exactly this case (open assignment in the incoming year, none in the outgoing one). It did not.

The lead, unconfirmed. The two school-year rows both carry updated_at = 20:06:18.329, so the flip transaction began then. Roster rows were still being written at 20:05:53 and 20:06:33 — the upload and the activation overlapped. Somebody created while the flip was running would be made inert, because the upload still saw the old year as active, and would be invisible to 4b, because they did not exist in its snapshot. That fits, but it was not proven, and two earlier theories this same evening (duplicate records, never-set-up records) looked just as good and were both wrong. Confirm against creation timestamps before changing anything.

The guard that would have made all of this a five-minute review. The flip already counts what it is about to deactivate and reports the number afterwards. It should show who, and require confirmation, before doing it. None of the three causes would have reached production unnoticed.

Why it took four rounds to find. Every diagnostic and repair written on 24 Aug carried role <> 'NO_ACCESS', because the investigation began with people locked out of signing in. A teacher IS a NO_ACCESS person, so that silently excluded all 2,061 of them. The staff repair fixed 46; the 313 teachers in the identical state were left, and surfaced only as Brendan found them school by school. The scope error was spotted and corrected in the diagnostics but the repair was never re-run with the correction.

What was NOT a fault. Of 14 teachers checked against the source spreadsheet, 11 were simply absent from it — Catalyst did what it was told. 89 teachers with no roster row were reviewed and are correctly inactive. Duplicate records were ruled out: one in the whole network, and it reads as a real school move.

Scripts from the investigation are in scripts/ — diagnose-inert-teachers.sql is the one that found the real shape, and repair-inert-teachers.sql is what fixed it.

Make the 0.7 proficiency threshold a setting too

New, 27 Aug. The other half of the rescore rule, deliberately left out of #38's sibling work.

The rescore deadline is now a setting. The score that puts somebody in the queue at all is still 0.7, hardcoded in about a dozen places.

Why this is a bigger change than the windows were

A deadline change moves dates. A threshold change alters who is flagged at all — raise it and teachers who were fine are suddenly in the queue; lower it and people leave it. It also decides the red/green colouring across the Action Center and the district view, so it is not confined to one feature.

Where it lives. Server: routes/observations.ts (both rescore branches), routes/ai.ts (three), services/ai-service.ts (five, including the assistant's own system prompt, which states the number to users). Client: PROFICIENCY_THRESHOLD in action-center.tsx, used in several places, plus the district dashboard.

The infrastructure already exists. system_settings is a single network-wide row with an audit trail, and the AI prompt already substitutes a live value for the rescore window — the same mechanism would carry the threshold. The work is finding all dozen sites and deciding what happens to people already in the queue when it moves, which is the same question the windows raised.

Worth doing deliberately rather than riding along on a deadline change, which is why it was split out on 27 Aug.

A teacher has two different pages

New, 27 Aug. Found by landing on the wrong one and assuming the app had broken.

Clicking a teacher's name in the Action Center and clicking one on the dashboard lead to different pages. Both are “the teacher's page” to anybody using them, and nothing on screen says which one you are on.

What each one is, and why this keeps costing something

The profile — dashboard, click a teacher. Observation history, scores, the detail modal, editing, the walkthrough tag. This is the one everything gets built into.

The action steps page — /teacher/:employeeId, reached from the Action Center. Open and Mastered action steps, and a button to add an observation. No observation history at all. Added 13 Jul as “Add Action Step UI” (117b685) for working through somebody's overdue steps, and it has never shown observations.

How it surfaced. Arriving from the Action Center on 27 Aug it looked as though the walkthrough tag and the observation editing had disappeared. Nothing was broken — that page has no observation boxes to put them on. But the page gives no clue that it is a different thing, so the reasonable conclusion was that the app had lost a feature.

Why it will keep happening. Everything added to observations lands on the profile only. Today that is the walkthrough tag and the date, time and teacher editing; next time it will be something else. Nothing forces the two to agree, and only one of them is ever remembered.

The decision. Not a refactor to schedule but a question to answer: should a teacher have one page? Roughly:

  • One page. The Action Center links to the profile, which grows an action-steps section. Everything about a teacher in one place, and the drift ends. Most work, and the profile is already long.
  • Keep both, make them obviously different. Retitle the action steps page so it does not read as the teacher's profile, and link to the full profile from it. Cheap, and honest about what it is.
  • Fold action steps into the profile and retire the route. The Action Center deep-links to the profile with the action steps section opened. One page, one URL, and the deep link still lands where it should.

Same shape as the department classifier and the two rubric copy paths — one idea implemented twice, drifting because nothing holds them together. Worse here because it is the part people see.

A teacher-facing view of their own observations

Every role in Catalyst today is an observer. The only state a teacher can hold is NO_ACCESS, which is blocked at login outright — so there is no such thing as a person who can sign in and see only themselves.

The decisions this needs before any code

It is a new role, not a filter. Every authorization path assumes the signed-in person is looking at somebody. A teacher role needs its own scoping rule — your own records, nobody else’s — applied to observations, action steps and anything that aggregates.

What may a teacher see? Scores as numbers, or only the written feedback? Drafts, or published only? Their action steps, including overdue ones? An observation a coach has written but not shared? These are policy questions, and each one changes the shape of the work.

This is the largest item on the list. Worth splitting once those answers exist.

45

Own the production database account directly

Added 30 Aug, out of a review of how much of Catalyst depends on Replit. Pairs with #46. Neither is a move off Replit.

The real data lives in a PostgreSQL database called neondb. Neon is a separate company from Replit — Replit sets the database up on your behalf, which usually means the account holding it is Replit’s, not yours. Worth knowing which, because two things follow from it.

What it costs you today, and what owning it would fix

Production cannot be reached from a shell. A comment in artifacts/api-server/.replit-artifact/artifact.toml puts it plainly: the deploy is “the only place its credentials exist.” That is why a one-off repair to 158 people’s grade levels now runs on every single deploy — there was nowhere else to run it. Any future data fix faces the same problem and gets solved the same wrong way.

If Catalyst ever leaves Replit, the database leaves with Replit unless the account is yours. That turns a config change into a data migration of real staff records, at the worst possible moment.

The first step is a question, not a change. Find out whose account holds neondb. If it already sits under a Neon account in your name, most of this item is already done and the rest is just writing down how to sign in to it.

If it is Replit’s: the move is an export into a Neon project you own, then repointing DATABASE_URL. That is a one-way copy of live staff data, and it needs a window with the app switched off so nothing is written to the version being left behind. An evening or a weekend, never mid-week with leaders observing.

What it buys: a console into production, so the next data fix runs once instead of living in the deploy forever; backups you control and can restore from; and a future host change that is config only. What it changes for users: nothing. Same app, same address, same login.

46

Pin the Google sign-in return address in production

Added 30 Aug, same review as #45. Small, and the safer of the two to do first.

Signing in sends a leader to Google and Google sends them back to one exact address. Catalyst works that address out as it starts up, and when nothing tells it otherwise it falls back to a domain name that Replit supplies. So a Replit-side change to that domain would break sign-in for everybody at once, with no warning and nothing in the app to explain it.

The change, and why it needs care rather than effort

Where it lives: buildCallbackURL() in artifacts/api-server/src/lib/passport.ts already prefers a setting called GOOGLE_CALLBACK_URL and only falls back to the Replit domain when that setting is empty. The same Replit domain also builds the list of addresses the API will accept requests from, in artifacts/api-server/src/app.ts. So one missing setting quietly controls two things.

The work is two lines and one check. Set GOOGLE_CALLBACK_URL to the real production address in the deployment’s secrets, then confirm that the exact same address is listed in the Google Cloud console as an authorised redirect. The fallback then only ever applies in the Replit workspace, which is where it belongs.

Sign-in is all or nothing — if the setting and the Google console disagree by even a trailing slash, every leader gets “redirect_uri_mismatch” and none of them can get in. That is what makes this a careful change rather than a hard one: do it when there is time to test a real sign-in straight afterwards, not last thing on a Friday.

What it buys: a known-good return address that Replit cannot change out from under you, and one fewer place where the app assumes it is running on Replit.

One teacher lookup still reads the wrong year’s rubric

Found 31 Aug while investigating an observation at Washington Park HS that displayed nowhere. It was not the cause of that — recorded so it is not lost behind it.

Rubric sets are copied forward each year and keep the same short name, so “Q1” exists once for 2025–2026 and again for 2026–2027. One route asks for “Q1” without saying which year it means, and gets the oldest copy — then looks for observations scored against it and finds none. A teacher with a full year of observations comes back empty.

Where it is, why it is not biting yet, and why that is the reason to fix it

Where it lives: artifacts/api-server/src/routes/teachers.ts:46 — GET /api/teachers/:id resolves the rubric set from the ?quarter= name alone. Every other rubric lookup in the API pairs the name with the active school year. This is the only one left that does not.

This exact mistake has been fixed here before. .agents/memory/rubric-slug-year-filter.md was written after the same bug was found in the AI and rubric routes, and it says plainly that any lookup by name must be paired with the year. This route was missed at the time. The note is now accurate everywhere except here.

Nothing calls it today. No screen in the dashboard or the mobile app uses this endpoint — which is the only reason it has not caused an incident. It fails silently rather than loudly: no error, no empty state, just a teacher who appears never to have been observed. Whoever wires up the next screen to it inherits that, and will have no reason to suspect the endpoint rather than the data.

The fix is one line — add the active school year to the lookup, the way the other routes already do — plus a test that a teacher’s observations still come back after a year has rolled over. The test is the part worth having: the one-line change is easy to make again and easy to lose again.

What it changes for users: nothing today, because nothing reaches it. It removes a trap rather than fixing a visible fault.

Latest Action Step — the whole roster, not just the stragglers

e0508b3 → 831945f — 11 front-end unit tests, 6 integration

Every Intervention sub-tab was an exception list: who is late, who needs rescoring. None could show a teacher who has no action step at all, because a queue has nothing to put in that row. This one lists every teacher in the school with their most recent step — when it was assigned, when it is due, whether it has been mastered — filterable by grade, department and overdue. Read-only. It replaced the Overdue Action Steps tab.

The swap that could have quietly lost people, and what else came out of it

The overdue rule is the whole care of this item. The retired tab listed one row per overdue step; this one lists one per teacher and shows only their newest. Filtering on the displayed step would have dropped a teacher holding an overdue step from October who has since been given a fresh one in December — strictly worse than the tab being replaced, and invisible. So the overdue flag is computed across all of a teacher’s steps, the filter reads that, and a row whose newest step is fine but who is overdue elsewhere says so. Otherwise the filter looks broken: a matching row with nothing red on it.

Blank rows are the finding. A teacher with nothing is listed saying so, rather than omitted. That case is the reason the tab exists.

The scope narrowed on the day it was specified. Asked for as glows, grows and action steps; settled the same morning as action steps only. The glow/grow half raised a question with no clean answer — the two live on the same observation and either can be left blank, so a “most recent” of each either shows a lot of empty cells or silently reaches back to different visits. Worth its own item if it is ever wanted.

Carried across deliberately: days overdue, Assigned By, and the “extended N×” badge from #16. Losing that badge would lose the signal that a teacher is stuck rather than late once.

Scoping. Steps are filtered by snapshot_school_id, as /action-steps/latest already does, so a transferred teacher cannot drag their previous school’s steps onto the list. Steps hanging off unpublished drafts are excluded — modern drafts hold their intended step on the observation, but ones written before #37 created real rows.

A rename rode along. The query key was overdueActionSteps and is now latestActionSteps, across its consumers and tests, so the name does not outlive what it describes. Every existing invalidation site followed it unchanged, so the new tab refreshes on exactly the events the old one did. GET /action-steps/overdue is untouched and still tested; nothing in the app calls it now.

Two rounds of polish after first use. The tab moved to second behind Usage; the filters and table header now stay put while only the rows move; and the step text — which can run long — took the width the date columns did not need, clamped to three lines with the rest on hover. The yellow rule under the header became an inset shadow rather than the separate 3px row its sibling tables use, because a second row needs its own sticky offset and drifts out of place as the header moves.

Unrelated, and fixed in the same pass: the Usage table had kept its own light-grey header while every other table in the tool uses navy, Bebas Neue and a 3px yellow rule. It matches now. It is still the only sortable table here, so the active column is picked out in yellow — the old navy-on-grey cue is invisible against a navy header.

On the testing. The client filter rule was pulled into its own module so the overdue case could be pinned down; it is easy to get subtly wrong and expensive to notice. The six endpoint tests could not be run locally — there is no database on a developer machine — so #12 gave them their first real run, and went green.

Continuous integration

221c606 → 6f8e041, fixes in 2c7e36b and a805df0

Every push now runs the whole suite — type checks, both front ends, the no-database tiers, the schema check and the full database suite against a throwaway Postgres — on GitHub’s machines, in about nine minutes. A red mark appears on the commit before anything is published, rather than depending on somebody remembering to run it.

It found two real bugs before it ever went green

Neither bug was in the workflow. Both had been in the app for months, invisible because every environment we had ever tested in happened to hide them. That is the entire argument for building a machine that starts from nothing.

First: a column that lied. schools.school_number has been NOT NULL in the database since migration 0006, and the form validator has always said “School Number is required”. The Drizzle declaration never caught up and claimed it was optional. The schema check had only ever run against dev, which passes — an environment set up with push instead of migrate never gets the constraint. Run against a database built from the migrations, the disagreement surfaced immediately.

Second, and worse: nobody could log in. configurePassport() returns early when the Google credentials are absent — correct, there is no strategy to register. But the two lines that store a signed-in user in their session sat below that return, and they have nothing to do with Google. Without OAuth configured, passport had no serializer at all and every login failed with a 500, dev-login included. That was all 403 integration tests, dying at their first line.

It had never been seen because Replit sets that credential, so the early return never mattered. A CI runner is the first machine we have ever pointed at this that does not have it — which is precisely the machine a new environment, or a new developer, would be.

The build stamps a fingerprint of its sources into the bundle, the server reports it on /api/healthz, and the script recomputes it and compares. Both sides call one function — two implementations of a hash drift, and a silently-drifted staleness check is worse than none.

It fingerprints the working tree, not HEAD. The original plan was to compare against git rev-parse HEAD, which would have missed the most common case entirely: edit a file, re-run tests, never restart. HEAD has not moved, so a commit check sees nothing wrong.

Two deliberate limits:

  • Test files are excluded — tsx runs them directly and they are never bundled. Counting them would force a restart after every test edit, which is the fastest way to get the check switched off for good
  • It stops rather than restarting — the server may belong to another terminal, and cleanup() already refuses to kill a server it did not start. WAIT_FOR_API_ALLOW_STALE=1 is the escape hatch

Not covered: a dependency bump changes the bundle without changing the hash. Rare inside a test loop, and the alternative fires on every install.

Production deploys apply their own migrations

post-merge.sh only ever covered the workspace database. The deployed service had its own and nothing migrated it — which surfaced as three failed publishes.

What was actually wrong

Production’s schema had been maintained with drizzle-kit push, which never writes the tracking table, so migrate started at 0000 and collided with an existing type. Each retry collided one migration later — 0000, then 0008, then 0009 — and each collision was the evidence for baselining the next.

The build step now runs the same things post-merge does, in the same order: compile, baseline the tracking table, migrate, then verify with #3.
