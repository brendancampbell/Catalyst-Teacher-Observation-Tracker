Clear fifteen stray test school years in dev

Do before #4 — it may be the cause.

Tool built (dd1d971) — not yet run. Twelve Test Year (slug cross-year), plus Test, New Test and a TST-INSIGHTS-OLD-YR-…. Suites create school years and never delete them.

Next: dry run in Replit, read it, then --apply.

Why it is filed next to the flake

A suite that leaves rows behind is a suite that can leave other state behind. This is the most concrete evidence available that test cleanup is incomplete, and #4 is exactly the shape that would produce.

Worth clearing regardless — the School Years admin tab lists all seventeen, of which two are real. Choosing a year to activate during a rollover means picking a real one out of that list, at the moment when picking wrong takes the app down.

How the tool refuses to be dangerous. It deletes only names a test provably creates — five patterns read out of the suite, each recording the file that produces it. Test and New Test are not among them: no test makes those names, so a person did, and they are reported rather than removed. Referencing tables are discovered from pg_constraint, and only an explicit allowlist may be deleted alongside a year — a table that gains a school_year_id later is unknown, and unknown means stop. Any year carrying observations or action steps is skipped. Dry run by default; writes happen in one transaction that verifies its own delete count.

The patterns began as SQL LIKE prefixes, which also claimed TST Rollover 123 (keep) — a name someone might pick precisely to keep it. A unit test caught that before it ran anywhere.

The Replit Run button exhausts the container

New, 20 Aug. Deferred by choice, not by priority — see below.

Running the app in Replit dies with SIGABRT before any code loads. Node aborts inside NodePlatform because uv_thread_create failed — the container would not give it another thread.

The cause, what is still unmeasured, and why this may belong at P1

.replit’s Project workflow is the Run button. It is mode = "parallel" with 48 tasks, 12 of which launch Playwright with Chromium. Every task is pnpm → node → tool, and each node sizes its V8 pool from the host’s core count, so each wants 12–20 threads before doing anything. Meanwhile the preview needs three dev services of its own.

Whichever process starts once the ceiling is reached is the one that dies, which is why the victim moves around and why it looks intermittent.

Measured so far: 270 pids at idle against a pids.max of 1024. That is the baseline, not the peak — it neither confirms nor refutes the ceiling. Still to capture: peak pids during the crash, ulimit -u, the cgroup memory limit, and what the 270 idle processes actually are. If they are orphans from earlier Run clicks, the headroom shrinks with every click and that is a second, separate fix.

Intended fix: the Run button starts the app; validations move to a separate mode = "sequential" workflow. Optionally cap NODE_OPTIONS=--v8-pool-size=2 and UV_THREADPOOL_SIZE=2 as a backstop.

Why it arguably outranks #5 and #4: those 48 parallel tasks include most of the integration suite, sharing one dev server and one database. Tests that create school years, flip the active year and deactivate people running concurrently is not just a resource problem — it is a plausible source of the stray years in #5 and the flake in #4. Fixing this first might make both disappear.

Record sign-ins

New. Split from #20 — different shape, different urgency.

Nothing records a login today. Whenever this ships, the data starts at zero — so every day it waits is a day of history that cannot be recovered.

Why it is ranked above work that matters more

There is no last_login on people, no audit table, and the session table belongs to connect-pg-simple — it holds live sessions with an expiry, not a history. So unlike observation and action step counts, this cannot be backfilled.

That is the whole argument for doing it early. The report in #20 can be built any time; the data only accrues once capture exists. Shipping a bare column now and the report later loses nothing, while the reverse loses months.

To decide: a last_login timestamp on people is one migration and answers “who has never signed in”. A row-per-login table answers “how often” and “when”, which is what #20 actually wants — but it grows forever and needs a retention rule. Both write from the same two places: the Google callback and deserializeUser.

8

Integration tests refuse to run against a stale API server

b737266

wait-for-api.sh reused whatever answered on port 8080. Since pnpm run dev is build && start, that server is a compiled snapshot which never picks up a later edit — so new tests ran against old code and nothing said so.

Why it is not the commit check the item asked for

The build stamps a fingerprint of its sources into the bundle, the server reports it on /api/healthz, and the script recomputes it and compares. Both sides call one function — two implementations of a hash drift, and a silently-drifted staleness check is worse than none.

It fingerprints the working tree, not HEAD. The original plan was to compare against git rev-parse HEAD, which would have missed the most common case entirely: edit a file, re-run tests, never restart. HEAD has not moved, so a commit check sees nothing wrong.

Two deliberate limits:

  • Test files are excluded — tsx runs them directly and they are never bundled. Counting them would force a restart after every test edit, which is the fastest way to get the check switched off for good
  • It stops rather than restarting — the server may belong to another terminal, and cleanup() already refuses to kill a server it did not start. WAIT_FOR_API_ALLOW_STALE=1 is the escape hatch

Not covered: a dependency bump changes the bundle without changing the hash. Rare inside a test loop, and the alternative fires on every install.

8 unit tests against throwaway file trees, no database. The no-DB tier is 67/67.

Schema-sync verifies indexes, and gates the deploy

e5a3e02 — shipped with #7

Three new drift classes — MISSING INDEX, TYPE MISMATCH, NULLABILITY — and check:schema-sync now runs in the production build after migrate.

The two deliberate limits, and how it was verified

The mapping is not guesswork. Probing the live schema showed exactly sixteen distinct getSQLType() values and twenty-five declared indexes, all named, so the translation table covers what this codebase uses rather than what Postgres permits.

Because it gates the deploy, two things it deliberately will not do:

  • A type it cannot map with certainty is listed as unchecked, never reported as drift
  • Index comparison is one-directional — Postgres creates its own for primary keys and unique constraints, and those never appear in Drizzle’s config

A gate that cries wolf gets deleted, and then it protects nothing.

19 unit tests, no database required. Verified end to end by dropping people_rescore_school_year_idx in dev: pass, then fail naming that exact index, then pass again once restored.

Production deploys apply their own migrations

post-merge.sh only ever covered the workspace database. The deployed service had its own and nothing migrated it — which surfaced as three failed publishes.

What was actually wrong

Production’s schema had been maintained with drizzle-kit push, which never writes the tracking table, so migrate started at 0000 and collided with an existing type. Each retry collided one migration later — 0000, then 0008, then 0009 — and each collision was the evidence for baselining the next.

The build step now runs the same things post-merge does, in the same order: compile, baseline the tracking table, migrate, then verify with #3.
