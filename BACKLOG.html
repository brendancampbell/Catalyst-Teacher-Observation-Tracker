A test database that can be rebuilt from empty

26b9ccb and the run before it — 326/326 from nothing

The suite used to run against the dev database — the same one used for clicking around. pnpm test:clean now stands up a throwaway Postgres, migrates it, seeds it, runs the tests and throws it away. Every run starts identical, and nothing a test leaves behind can reach real data.

What it caught on its first honest run

Ten tests failed that had always passed. All ten were the same thing: migration 0001 creates assignments_user_active_uniq, which allows a person one open assignment across all years. A staged rollover needs the opposite — somebody holds the running year and the year being staged at once, and the flip closes the first. Every staged roster row conflicted and ON CONFLICT DO NOTHING swallowed it, silently.

The fix had already been written. It just landed in lib/db/src/migrations/, a directory nothing runs — not in the drizzle journal, not pointed at by the config. It reached dev and production only because somebody ran it by hand. Any database built from the migrations got the wrong rule. 0012_drop_stale_assignment_index.sql now does it properly, and a README in that directory says it is not wired up.

Production was never affected, and the 2026–27 rollover proves it: staging a roster while everyone still held current-year assignments would have failed on every row if that index were there.

Why nothing caught it sooner. check:schema-sync compares in one direction only — it reports indexes the schema declares and the database lacks, never extra ones, because Postgres makes its own for keys and flagging those would make every deploy noisy. An index nobody declared is exactly the blind spot that leaves. A database built from empty is the only thing that could have found it.

Four wrong guesses preceded the answer, each costing a nine-minute run. What settled it was instrumentation, not theory: a state dump in the harness, self-verifying assertions in both fixtures, and finally a probe that ran the SELECT and the INSERT side by side and listed the indexes.

This was the prerequisite for #12 and the root of #4. A robot can now run the suite, because it can build its own database.

15

“Mastered” can be undone

f6f06d8 — 6/6 integration, no migration

Mastery was one-way. Marking a step was a click, editing a mastered step is refused by business rule, and there was no inverse — so a misclick could not be undone from the interface at all.

Three decisions behind it

Same permissions as marking it. Whoever can say “done” can say “not done after all”, so a coach who misclicks does not have to find a principal to fix it.

A quiet revert, not a recorded event. This exists to fix a mistake, so the step goes back to exactly how it was — including its original due date. That can put it straight back on the overdue list, which is right: undoing a mastery means the work was never finished.

The link to the mastering observation is cleared along with the timestamp and the person, or the step would still claim it was mastered during an observation that no longer says so. The observation itself is untouched — it happened, and its record stands. There is a test for that.

Refused: undoing a step that is not mastered, one from a previous school year (same rule as marking), and one belonging to another school.

16

Repeating an action step extends it instead of duplicating it

4e80b5c — migration 0011 · 6/6 integration, 13 unit

“Repeat last action step” copied the text and due date into the new action step box, so saving created a second open step saying the same thing. A teacher working on one thing for a term collected a list of identical steps.

What it does now, and the guard that was easy to miss

It extends the existing step: same step, same wording, new date. The old button also prefilled the old due date — by definition in the past when you are repeating — so it showed a validation error every single time. The date field now starts empty.

Extensions are recorded, not just applied. Moving the date alone would quietly erase that a step has been extended three times and was originally due in October, which is the signal a teacher is stuck. Each push keeps both dates, who did it, an optional note, and the observation it happened during. The profile shows “Extended 2× · originally due 3 Oct”; the Action Center flags extended steps in the overdue list, because overdue after two extensions is a different situation from overdue once.

Extend or assign, never both. Two different answers to “what next for this teacher”. The new step box is hidden while extending and its contents cleared, and the server refuses a payload carrying both, so no other route can do it either.

The guard that was easy to miss: draft autosave calls the server on every keystroke. Without a check, each save would add another extension row and push the date again — the same duplication this feature removes, one level down. An extension from the same observation is edited in place, and the original due date is kept rather than tracking the last autosave.

Also refused: extending a mastered step (that would reopen finished work) and extending a step belonging to a different teacher.

Catalyst records who uses it, and when

44dd11e, 995c15b — migration 0010 · 4/4 integration, 9 unit

Nothing recorded a sign-in: no last_login, no audit table, and the session table holds live sessions with an expiry, not a history. The data could only ever start from the day this shipped, which is why it went in before the report that consumes it (#20).

Why it counts days rather than sign-ins, and where the hook had to go

The finding that set the design. The session cookie is seven days and not rolling, so somebody who opens Catalyst every single day re-authenticates about four times a month. A “logins per user” report built on OAuth callbacks would show the most active principal in the network as barely using the tool.

So it records one row per person per day they used Catalyst. That answers who uses this, how often, and who has never signed in at all — and it is bounded, at most one row per person per day, so no retention policy is needed. sign_in_count rides along, because one integer also answers “how often are people being made to sign in again”.

The hook sits in deserializeUser, and that is load-bearing. It runs before applyImpersonation swaps req.user, so an admin impersonating someone is recorded as the admin — otherwise a management report would credit people with activity they had no part in. Moving it later would break that silently, so an integration test pins it.

Fire-and-forget, failures logged and swallowed: this is on the hot path for every authenticated request, and telemetry that can hang or 500 the app is worse than no telemetry.

Dates are Eastern, not UTC. Under UTC a principal writing observations at 8pm would have it filed as the next day, and one evening would count as two days of activity. Tested on both sides of a daylight saving change — the bug that would misfile exactly one evening a year and never be noticed.

Two failures on the way, both instructive. The first run died with ECONNREFUSED after wait-for-api.sh announced “ready” — the server was refusing to boot against an unapplied migration and said so in a log nothing read. Fixed separately in bc46f57. The second was the test racing its own fire-and-forget write: test 1 saw no row while test 2 found exactly one, which is the signature of checking too early rather than of a write that never happened.

The Replit Run button no longer exhausts the container

a9e7478 — measured: peak 272 pids, was climbing toward 1024

Running the app in Replit died with SIGABRT before any code loaded. Node aborted inside NodePlatform because uv_thread_create failed — the container would not give it another thread.

What it was, and the two-line change that fixed it

.replit’s Project workflow — the Run button — was mode = "parallel" with 48 tasks, 12 of which launch Playwright with Chromium. Each is pnpm → node → tool, and every node sizes its V8 pool from the host’s core count rather than the container’s share, so each wanted 12–20 threads before doing any work. Several hundred started at once while the preview was separately trying to start three dev services. Whichever process started once the ceiling was reached is the one that died — which is why the victim moved around and it looked intermittent.

Every one of those 48 is isValidation = true. Replit’s agent appends one per feature it builds; they are meant to be run individually. The Run button pointing at all of them in parallel was accumulated accident, not a decision — and it never started the app at all. That is the artifact dev services, which is why the crash log showed the dashboard’s Vite dying while the workflow was doing something else entirely.

So the Run button now reports where the app is served and how to run checks, and the 48 tasks moved verbatim to a Validate All workflow. Both omit mode, which defaults to sequential. An 8-line diff, with every individual validation workflow untouched.

Confirmed by measurement, not just by the crash stopping: peak 272 pids against a 270 baseline across a Run click — roughly two processes where it used to climb toward pids.max of 1024.

Not added: a global NODE_OPTIONS=--v8-pool-size=2. It would help, but .replit env reaches the deployed server too, and quietly halving production’s thread pool to fix a dev crash is the wrong trade.

Sequential is not a workaround: these tests share one dev server and one database, so running them at once is wrong for correctness as much as for threads. Watch #4 — concurrent execution was its leading explanation, and that mechanism is now gone.

The suite no longer leaks school years

a0e6578 — verified: 298/298, then 2 years and nothing to clean

Fourteen of #5’s fifteen strays came from one test whose cleanup deleted the school year before the rubric set pointing at it. That raises a foreign key violation, and a .catch(() => {}) swallowed it — so the test passed green and the year survived. Every run.

The bug, the fix, and the guard that outlives both

The culprit was test-rubric-category-domain-validation.ts, not the file first credited with it. Its cleanup even carried a comment asserting the delete cascades. It does not: rubric_sets.school_year_id is ON DELETE NO ACTION — a fact the cleanup tool prints at the top of every run. The other two year-creating tests delete their rubric sets first and never leaked.

Fixed three ways:

  • Rubric set first, then the year
  • A cleanup failure is reported, not swallowed — silent teardown is how this survived for months
  • A timestamped name, like every other scratch year. The fixed name is why there were fourteen identical rows rather than one traceable to a run; the old name is still recognised so an older checkout’s strays can be cleared

The guard matters more than the fix. A unit test now reads the suite rather than trusting the cleanup’s pattern list: every insert(schoolYears) name in src/test-*.ts must be one the cleanup can find again. Verified by planting a year called My Very Own Year — it fails and names the file and the string. A scratch year the cleanup cannot recognise is one that accumulates forever, which is precisely what happened here.

That guard exists because the list was already wrong. It credited the wrong test with the name, and reading the code did not catch it — reading the suite did.

Also fixed a defect in the cleanup report itself: it listed years it was leaving alone without their dependent counts, so “inactive, named Test” read as “empty”. Two such years held 1,949 and 2,226 assignment rows — staged rollover rehearsals — and were deleted on that mistaken assurance. The report now prints what each one holds.

Cleared the school years left behind by tests

dd1d971, 0b85557 — 19 years → 4

Dev had grown to 19 school years, of which 2 were real. Deleted 15; the two human-made ones were left for review.

How a destructive script was made safe enough to run

Deleting a school year is not safe in general — observations, action steps and rubric sets are all scoped by one — so cleanup:test-school-years fails closed at every decision.

  • It deletes only names a test provably creates: five patterns read out of the suite, each recording the file that produces it
  • Test and New Test were not touched — no test makes those names, so a person did
  • Referencing tables are discovered from pg_constraint, and only an allowlist may be deleted alongside a year. A table that gains a school_year_id later is unknown, and unknown means stop
  • Any year holding observations or action steps is skipped, as is one whose rubric sets are pinned by an observation elsewhere
  • Dry run by default; one transaction that verifies its own delete count before committing

The pattern list is its own module with 8 unit tests, following schema-compare.ts: it decides what gets deleted, so it is the risky part. Those tests paid for themselves immediately — the patterns started as SQL LIKE prefixes, which also claimed TST Rollover 123 (keep), a name someone might choose precisely to keep it.

This is a broom, not a fix. 14 of the 15 came from one test that reuses a fixed name and never tears down — see #23, or this becomes a recurring chore.

Integration tests refuse to run against a stale API server

b737266

wait-for-api.sh reused whatever answered on port 8080. Since pnpm run dev is build && start, that server is a compiled snapshot which never picks up a later edit — so new tests ran against old code and nothing said so.

Why it is not the commit check the item asked for

The build stamps a fingerprint of its sources into the bundle, the server reports it on /api/healthz, and the script recomputes it and compares. Both sides call one function — two implementations of a hash drift, and a silently-drifted staleness check is worse than none.

It fingerprints the working tree, not HEAD. The original plan was to compare against git rev-parse HEAD, which would have missed the most common case entirely: edit a file, re-run tests, never restart. HEAD has not moved, so a commit check sees nothing wrong.

Two deliberate limits:

  • Test files are excluded — tsx runs them directly and they are never bundled. Counting them would force a restart after every test edit, which is the fastest way to get the check switched off for good
  • It stops rather than restarting — the server may belong to another terminal, and cleanup() already refuses to kill a server it did not start. WAIT_FOR_API_ALLOW_STALE=1 is the escape hatch

Not covered: a dependency bump changes the bundle without changing the hash. Rare inside a test loop, and the alternative fires on every install.

8 unit tests against throwaway file trees, no database. The no-DB tier is 67/67.

Schema-sync verifies indexes, and gates the deploy

e5a3e02 — shipped with #7

Three new drift classes — MISSING INDEX, TYPE MISMATCH, NULLABILITY — and check:schema-sync now runs in the production build after migrate.

The two deliberate limits, and how it was verified

The mapping is not guesswork. Probing the live schema showed exactly sixteen distinct getSQLType() values and twenty-five declared indexes, all named, so the translation table covers what this codebase uses rather than what Postgres permits.

Because it gates the deploy, two things it deliberately will not do:

  • A type it cannot map with certainty is listed as unchecked, never reported as drift
  • Index comparison is one-directional — Postgres creates its own for primary keys and unique constraints, and those never appear in Drizzle’s config

A gate that cries wolf gets deleted, and then it protects nothing.

19 unit tests, no database required. Verified end to end by dropping people_rescore_school_year_idx in dev: pass, then fail naming that exact index, then pass again once restored.
